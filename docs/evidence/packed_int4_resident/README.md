# Resident packed-int4 CPU evidence

The claim-ineligible benchmark receipt
`resident-int4-dgx-v1.json` is the original canonical output from the isolated
DGX run of the exact source bytes bound inside the receipt.

- Receipt SHA-256:
  `2b2804acaa720ee7f39520d918d4b20096ae1c65b7d7cca7caeb34e29b8adc48`
- Receipt bytes: 211,096
- Platform: Linux aarch64, PyTorch 2.12.1+cu130, one CPU thread
- Shape: 5,924 gallery vectors by 128 dimensions, one query per call
- Protocol: 100 warm-ups and 10,000 raw timing samples per arm
- Exactness: all three score matrices are bit-identical

| Execution layout | Bytes/vector | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| Packed int4, decoded every call | 66 | 1,070,833 ns | 1,103,712 ns | 1,117,967 ns |
| Resident int8 + f16 norm | 130 | 290,700 ns | 297,275 ns | 302,331 ns |
| Resident float32 + f32 norm | 516 | 63,696 ns | 66,031 ns | 68,431 ns |

Resident int8 is 3.71 times faster at p95 than the existing per-call decode path
while remaining 3.97 times narrower than resident float32. Resident float32 is
4.50 times faster than resident int8 at p95. These are memory/latency Pareto
points, not evidence that integer matrix multiplication beats float BLAS. If the
packed source and int8 execution layout coexist, their combined layout is 196
bytes/vector.

The resident layout was constructed in 2,771,160 ns. The process high-water RSS
was 550,793,216 bytes; this is the whole Python benchmark process high-water
mark, not an incremental allocation attributed only to the resident layout.

The performance arm required an observed successful `torch._int_mm` capability
probe; the portable exact float fallback could not satisfy the receipt. The
isolated scratch directory and generated bytecode were explicitly removed after
the result was copied.
