The **exploratory official-quality gate** carries forward the TRAIN-only per-seed rule: freeze packed Recall@1 and mAP@R point estimates must each be at least their same-seed control; the paired product-bootstrap 95% lower bound for Recall@1 must be greater than −0.5 percentage points for each seed. Report the three-seed mean and seed range separately; the product bootstrap conditions on the reused TEST product set and does not measure training-seed uncertainty. If any pair fails, retain the training flag as a documented SOP TRAIN-cost option but do not promote its checkpoint or use further TEST reads to tune it. Passing permits only an exploratory official-quality comparison, not a current SOTA claim. The dated published UNICOM 91.2% Recall@1 SOP value is a reference, not a matched local control.

The **serving gate** uses the same six checkpoints and an interleaved matched image-to-top-10 harness. First require the public loader at `fp32_autocast` to reproduce the offline gallery bytes and exact packed top-10 on fixed TRAIN query images; separately measure the default `fp16_native` query path against the intended offline gallery and report any code/rank/quality difference. Do not inherit offline quality for a mismatched precision path. Then measure batch 1 and 32 decode-to-result latency, throughput, peak memory and cold start against the paired full-train checkpoint with identical hardware, images, gallery, scorer, precision and arm order. Report p50/p95 as diagnostics; any p99 certification needs at least 10,000 calls per cell and the repository's paired-block bootstrap gate. Freezing only changes training, so serving speed is expected to be similar and is not inferred from training wall time. A provenance, parity or quality failure blocks checkpoint promotion; a serving failure blocks that deployed precision configuration.

## Public serving parity diagnostic

The first serving gate **failed** for seed 179024, both arms. On 32 fixed SOP TRAIN images, the public batch-32 query API using the stored batch-64 training gallery matched exported packed codes for 10/32 control and 11/32 freeze images at `fp32_autocast`; exact top-10 matched 30/32 and 29/32. With the default `fp16_native`, codes matched 2/32 for each arm and top-10 matched 28/32 and 26/32. Top-1 matched 32/32 in all four small diagnostics; that is not a full quality result. Raw query IDs, image hashes, source hashes and results are in `docs/evidence/compact_metric/sop-siglip2-substrate-v1/sop-true-freeze-serving-179024/`.

An isolated diagnostic temporarily raised the encoder batch cap to 64 and queried the first 64 TRAIN rows, matching the offline export's batch shape. At `fp32_autocast`, codes, inverse norms and top-10 all matched **64/64** against the stored export. At `fp16_native` with the same batch shape, codes matched 6/64 and top-10 54/64. This isolates batch shape as the FP32 mismatch and half-weight inference as an additional mismatch. The diagnostic monkeypatch is archived as `batch64-diagnostic.py` and is **not** production code. The public API remains capped at 32. The frozen exact parity gate therefore blocks checkpoint promotion and any inference that official offline quality is served unchanged. A new production path needs a gallery exported and evaluated at the actual serving batch/precision, or an explicitly measured alternative that meets both quality and latency gates; padding every query to 64 would add encoding work and has not been shown to meet the performance target.
